## 1. 数据库约束实测（2026-10-27）

| # | 操作 | 预期 | 实际报错 | 结论 |
|---|---|---|---|---|
| 1 | 插入 `code=' EQ-A001'`（前导空格） | 拒绝 | `ERROR 3819 Check constraint 'equipment_chk_1' is violated` | ✅ |
| 2 | 插入 `code='eq-a001'`（小写） | 拒绝 | `ERROR 1062 Duplicate entry 'eq-a001' for key 'equipment.code'` | ✅ |
| 3 | 插入工单 `equipment_id=999` | 拒绝 | `ERROR 1452 foreign key constraint fails` | ✅ |

**结论**：CHECK、UNIQUE、FOREIGN KEY 三条约束均在数据库层生效；应用层即使漏校验，也写不进脏数据。

> 补充：`ERROR 1451`（不能改/删被引用的父行）也在改造前实测过 —— 这正是把 `code` 主键改成 `id` 代理主键的直接原因。

## 3. 软删除三重验证（2026-11-05）

`DELETE /api/repair-orders/{id}` 之后：

| 检查点 | 结果 |
|---|---|
| 接口 GET 该工单 | **404** ✅ |
| 列表 `total` | 3 → 2 ✅ |
| MySQL 里那行 | **仍在，`deleted=1`** ✅ |
| 再 DELETE 一次 | **404** ✅ |

**结论**：数据未被物理删除，仅被标记并排除在查询之外。三项同时成立才算软删除生效 —— 只看接口 404 分不清软删还是硬删。
